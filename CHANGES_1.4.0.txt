e2xray 1.4.0
============

Fixed: every hostname-based configuration deadlocked (this is the "red internet
light / no connectivity" report)
--------------------------------------------------------------------------------
From a user log:

    transport/internet/websocket: failed to dial to cdn2.example.cfd:443 >
      dial tcp: lookup cdn2.example.cfd on 1.1.1.1:53:
      read udp 10.255.0.1:36577->1.1.1.1:53: i/o timeout

The source address of that DNS query is 10.255.0.1 - the TUN interface. To dial
the proxy server Xray must resolve its hostname; the lookup was routed into the
tunnel; the tunnel could not exist until the lookup finished. A closed loop.

apply_socket_options already stamps every socket Xray opens with fwmark 0xff,
but in TUN mode nothing ever acted on that mark. Only the explicit /32 route for
the proxy server escaped the tunnel, so the transport survived by accident while
every other socket the core opened - above all its DNS client - was swallowed.
Configurations whose address is a literal IP worked; configurations using a
hostname could never start, and took the receiver's connectivity down with them.

Two independent fixes, either of which is sufficient:

  * A policy rule at priority 999 sends fwmark 0xff to a private table whose
    only route is the receiver's real default. Xray's own traffic now always
    leaves through the physical interface. Rule order is now:

        999   fwmark 0xff    -> physical   (Xray's own sockets)
        1000  fwmark 0x2334  -> physical   (card-sharing)
        1001  from all       -> e2xray0    (everything else)

  * The server address is pre-resolved by the control script - which runs before
    the tunnel is armed, using the untouched resolver - and pinned into the
    generated configuration, so the core never has to resolve anything. The
    hostname is preserved wherever the handshake still needs it: TLS and REALITY
    serverName, the WebSocket and XHTTP Host header, and the gRPC authority. An
    explicitly configured domain-front is never overwritten, and an address that
    is already an IP is left untouched.

Added: the tunnel is verified before control is handed back
------------------------------------------------------------
Starting the core and capturing the network is not proof that traffic reaches
the internet. A dead or blocked server left the receiver fully tunnelled with no
way out - which is exactly what the "internet light turns red and we lose our
connection" reports describe.

A start now probes through the finished tunnel (three attempts, generous
timeouts so a slow receiver is not mistaken for a broken one). If nothing
answers, that backend is rolled back, the next one is tried, and if none works
normal networking is restored and the user is told plainly what happened
(TUNNEL_DEAD). The receiver is never left offline.

Added: ISP filtering of the server address is named
----------------------------------------------------
A blocked domain does not fail to resolve, it resolves to the censor's block
page - 10.10.34.0/24 on Iranian networks. e2xray used to route the tunnel into
that black hole and report a generic failure. Such answers are now recognised,
excluded from the bypass routes, and if nothing usable remains the start stops
with SERVER_FILTERED: the domain of this configuration is blocked on this
connection, use another one.

Tests
-----
Added coverage for address pinning: implicit SNI and Host inherit the hostname,
an explicit domain-front is preserved, gRPC authority and REALITY serverName are
carried over, and IP-literal or unresolved addresses change nothing.
